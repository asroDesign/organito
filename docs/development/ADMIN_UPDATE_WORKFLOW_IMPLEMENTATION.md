# به‌روزرسانی ZIP امن از پنل مدیریت

## نتیجه برای مدیر فروشگاه

در «کاربران و تنظیمات سامانه ← به‌روزرسانی امن سامانه» مدیر کل فایل ZIP نسخهٔ جدید را بارگذاری می‌کند. سامانه قبل از نمایش دکمهٔ اجرا، امضای ناشر، نسخه، فهرست مجاز فایل‌ها، اندازه و SHA-256 تمام محتوا را بررسی می‌کند. مدیر فقط پس از دیدن نسخه و تعداد فایل‌ها، اجرای آن را تأیید می‌کند. نیازی به SSH، تغییر فایل‌های پروژه یا نوشتن کد از طرف مدیر فروشگاه نیست.

## گام‌های اجرای نسخه

1. فایل ZIP حداکثر ۱۲۰ مگابایت دریافت می‌شود و در پوشهٔ خصوصی `storage/updates` با مجوز محدود ذخیره می‌شود؛ فایل‌ها در پوشهٔ عمومی رسانه قرار نمی‌گیرند.
2. parser محدودکنندهٔ داخلی ZIP مسیرهای traversal، نام‌های تکراری، پیوند نمادین، فایل‌های رمزگذاری‌شده، ZIP چندبخشی، تعداد/حجم افراطی و CRC نادرست را رد می‌کند.
3. امضای Ed25519 روی بایت‌های دقیق `manifest.json` با کلید عمومی نصب‌شده روی سرور بررسی می‌شود. هر فایل باید با مسیر/اندازه/هش امضاشده مطابقت داشته باشد. فایل خارج از manifest یا امضای ناشناخته رد می‌شود.
4. فقط `src/**`، `public/**`، migration با الگوی `drizzle/NNNN_*.sql`، `package.json`، `yarn.lock` و `next.config.ts` در release پذیرفته می‌شوند. `.env`، `storage`، `.next`، `node_modules`، `.git`، تنظیم PM2 و خود worker قابل جایگزینی نیستند.
5. اجرای release تنها در `NODE_ENV=production` و با `UPDATE_APPLY_ENABLED=true` فعال است. پیش از تغییر برنامه، worker یک dump قابل بررسی با `pg_dump` و کپی فایل‌های هدف می‌سازد. در نبود backup دیتابیس، اجرای release پیش از تغییر کد متوقف می‌شود.
6. dependencyهای نسخهٔ امضاشده با lockfile نصب می‌شوند، Next.js در پوشهٔ build جداگانه کامپایل می‌شود، سپس migrationها تک‌به‌تک در تراکنش و زیر advisory lock اعمال می‌شوند. عبارت‌های حذف/تغییر مخرب مانند `DROP`، `TRUNCATE`، `DELETE`، `UPDATE`، `RENAME` و `CASCADE` پذیرفته نمی‌شوند.
7. build جدید به‌صورت rename روی `.next` قرار می‌گیرد، PM2 reload می‌شود و `/api/health` تا ۶۰ ثانیه بررسی می‌شود. خطای build/reload/health باعث بازگرداندن فایل‌های کد و build قبلی می‌شود.

## آماده‌سازی یک‌بارهٔ سرور توسط پشتیبان فنی

پنل، کارهای روزمرهٔ مدیر را بی‌نیاز از کد می‌کند؛ نصب اولیه باید یک بار روی سرور انجام شود:

- اجرای پروژه باید self-hosted روی Node.js باشد، مسیر ذخیره‌سازی persistent و قابل نوشتن باشد، و PM2 نام برنامهٔ صحیح را اجرا کند.
- `pg_dump` باید روی همان سرور نصب و از حساب سرویس قابل اجرا باشد. قبل از deploy واقعی باید یک backup جداگانه روی مقصدی مستقل از دیسک اپلیکیشن هم برنامه‌ریزی شود؛ این worker فقط backup محلی امن می‌سازد.
- در پوشه‌ای بیرون مخزن، کلید Ed25519 ناشر ساخته شود: `yarn updates:keys /secure/location/update-signing`. کلید خصوصی فقط نزد سازندهٔ release باقی می‌ماند؛ فایل public را به `UPDATE_PUBLIC_KEY_PEM` بدهید و آن را در environment امن PM2 قرار دهید.
- پس از بررسی فرایند backup و نام PM2، environment برنامه شامل `UPDATE_APPLY_ENABLED=true`، `UPDATE_PM2_APP=organito-app` و `UPDATE_HEALTHCHECK_URL` صحیح شود و PM2 با env جدید reload شود. مقدار پیش‌فرض عمداً false است.

## ساخت فایل ZIP نسخه برای مدیر

سازندهٔ release با کلید خصوصی خارج از مخزن، ZIP را از فایل‌های انتخاب‌شده و migrationهای همان نسخه می‌سازد:

```sh
UPDATE_PRIVATE_KEY_FILE=/secure/location/update-signing/update-private.pem \
  yarn updates:package 2.1.0 /secure/location/releases/organo-2.1.0.zip \
  src/app/example/page.tsx drizzle/0065_example_change.sql
```

نام فایل‌ها به‌صورت صریح به سازنده داده می‌شود و مسیرها دوباره با allowlist بررسی می‌شوند. خروجی ZIP هیچ کلید خصوصی یا تنظیم سروری ندارد؛ همان ZIP از مسیر پنل به مدیر فروشگاه تحویل می‌شود.

## امنیت، سازگاری و محدودیت‌های عمدی

- فقط `super_admin` می‌تواند API را بخواند، بسته بفرستد یا اجرا کند؛ مسیر mutation هم CSRF و same-origin را بررسی می‌کند.
- امضای ZIP جایگزین اعتماد به ناشر است؛ امضای private key نباید به سرور یا بستهٔ نسخه برسد. افشای کلید خصوصی امکان ساخت release معتبر را می‌دهد و نیازمند rotation کلید عمومی سرور است.
- migrationهای این مسیر باید افزایشی و سازگار با نسخهٔ فعال قبلی باشند. worker snapshot دیتابیس می‌سازد اما به‌صورت خودکار dump را restore نمی‌کند و migration قبلی را destructive rollback نمی‌کند؛ این کار از حذف خریدهای ثبت‌شده پس از deploy جلوگیری می‌کند.
- برای اجرای مجدد بسته، نسخه باید جدیدتر از نسخهٔ ثبت‌شده باشد. تا پیش از نصب نخستین package، نسخهٔ فعلی «نامشخص» نمایش داده می‌شود.
- اجرای package در محیط development، serverless یا بدون PM2 عمداً غیرفعال است. در چنین محیطی، پنل نباید فایل‌های کد در حال اجرا را دستکاری کند.
- فضای آزاد کافی، `pg_dump`، binaryهای `yarn`/PM2، backup مقصد خارجی و سازگاری migration باید پیش از فعال‌کردن production روی staging بررسی شوند. این turn به دیتابیس production دست نزده و package واقعی اجرا نکرده است.

## بررسی آمادگی سرور و فهرست پشتیبان‌ها

صفحهٔ پنل اکنون پیش از نمایش وضعیت اجرایی، Node.js، production بودن محیط، کلید عمومی Ed25519، پرچم فعال‌سازی، اتصال دیتابیس، دسترسی نوشتن/فضای آزاد پوشهٔ خصوصی، `pg_dump` و PM2 را بررسی می‌کند. وضعیت هر شرط به سه حالت آماده، نیازمند توجه یا مسدود نمایش داده می‌شود؛ API هیچ مقدار secret یا نشانی اتصال را به مرورگر نمی‌دهد. دکمهٔ اجرا تنها وقتی فعال است که تمام شروط لازم آماده باشند.

در همان صفحه، تا ۲۰ پوشهٔ پشتیبان اخیر با نسخه، زمان ایجاد و وجود/اندازهٔ dump فهرست می‌شود. محتوای dump به مرورگر ارسال نمی‌شود و دکمهٔ restore وجود ندارد. restore دیتابیس زنده می‌تواند سفارش/پرداخت بعد از زمان پشتیبان را حذف کند؛ توسعهٔ بعدی باید مقصد جداگانه برای نسخهٔ آزمایشی، صحت‌سنجی restore و نگهداری چرخشی تعریف کند.

## مسیرهای کد

- `src/app/admin/updates/page.tsx` و `src/components/AdminUpdateCenter.tsx`: تجربهٔ پنل و نمایش وضعیت.
- `src/app/api/admin/updates/route.ts`: مجوز super-admin، CSRF، upload و صف اجرای worker.
- `src/lib/update-package.ts`: parser ZIP داخلی، حدود منابع، CRC، امضا، allowlist و بررسی manifest.
- `scripts/apply-update.mjs`: backup، install کنترل‌شده، build موقت، migration افزایشی، PM2 reload، health check و rollback کد.
- `scripts/create-update-package.mjs`, `scripts/generate-update-keys.mjs`: ابزار انتشار برای سازندهٔ محصول، نه مدیر فروشگاه.

## دمو و ادامه

صفحهٔ دمو: `/admin/updates`. در محیط توسعه دکمهٔ اجرای آپدیت عمداً خاموش است؛ امکان نمایشی‌کردن آن به معنی مجازبودن دستکاری سورس زنده نیست. محیط جاری کلید ناشر یا `pg_dump` production ندارد، بنابراین ZIP production بارگذاری یا اعمال نشد.

مرحلهٔ بعد: تکمیل حفاظت عملیاتی نسخه‌ها با مقصد پشتیبان مستقل، چرخش نگهداری و آزمون restore در پایگاه جدا؛ بازیابی خودکار دیتابیس زنده از پنل در دامنه نیست.
