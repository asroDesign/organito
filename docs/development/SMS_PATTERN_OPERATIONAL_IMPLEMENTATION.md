# عملیاتی‌سازی الگوهای پیامک

**تاریخ:** ۶ اکتبر ۲۰۲۶  
**مسیر توسعه:** مورد ۶ گزارش شکاف‌های ویماشاپ — پیکربندی و ارسال پترن سرویس‌های موجود

## بررسی صفحه مرجع در Chrome

صفحه [تنظیمات ویماشاپ](https://digikala.vimascript.ir/admin/settings/edit) در تب «درگاه پیامک» بررسی شد. نمونهٔ صفحه، سرویس‌ها را با وضعیت اتصال نشان می‌دهد و برای سرویس فعال کلید/تنظیم اتصال و ۱۶ جایگاه کد الگو دارد. کنار هر جایگاه راهنمای متن الگو و متغیرهای قابل جایگزینی باز می‌شود. متن راهنما تأکید می‌کند پترن باید ابتدا در پنل پیامکی ساخته و توسط همان سرویس تأیید شود؛ شناسهٔ همان پترن سپس در جایگاه متناظر ذخیره می‌شود. در دو راهنمای بررسی‌شده، نمونه‌ها شامل OTP با `{{token_one}}` و تغییر وضعیت محصول فروشنده با `{{token_one}}` و `{{token_two}}` بودند. صفحهٔ مرجع اتصال را «پنل متصل نیست» نشان می‌داد و هیچ تنظیمی در سایت مرجع تغییر یا ذخیره نشد.

مهم‌ترین نکتهٔ طراحی، جایگاه شماره‌ای به‌تنهایی نیست؛ سامانه باید رویداد پیام، کد پترن تأییدشده و نگاشت متغیرهای واقعی برنامه به placeholderهای همان پترن را یکجا نگه دارد. در پروژه ارگانو این رابطه در قالب هر رویداد نگهداری می‌شود تا برای مثال `{code}` و `{order}` به جایگزین‌های مورد انتظار پنل نگاشت شوند.

## تغییرات انجام‌شده

- برای هر قالب پیامک فیلد افزایشی `parameter_map` اضافه شد؛ این نگاشت با پیکربندی کلی SMS.ir تداخل ندارد.
- فرم افزودن/ویرایش قالب، متغیرهای متن را نشان می‌دهد و نام پارامتر مختص سرویس فعال را برای هر متغیر می‌گیرد. نگاشت ذخیره‌شده کنار کد الگو در کارت رویداد نمایش داده می‌شود.
- ارسال عادی رویداد و ارسال گروهی دستی نگاشت همان قالب را استفاده می‌کنند. پیام مستقیم رویدادی نیز در صورت وجود قالب فعال و شناسهٔ پترن، از API پترن سرویس بهره می‌برد؛ ارسال متنی آزاد کمپین همچنان مسیر متن عادی را دارد.
- ارسال پترن بر اساس قرارداد سرویس پیاده شده است:
  - **مدیانا:** `/sms/v1/send/pattern` با `patternCode` و شیء `parameters` نام‌دار. پاسخ موفق بدون بدنه در کنار HTTP موفق پذیرفته می‌شود.
  - **قاصدک:** `SendOtpWithParams` با `templateName` و placeholderهای `param1` تا `param10`.
  - **ملی‌پیامک:** `BaseServiceNumber` با `bodyId` و مقادیر مرتب‌شدهٔ `text`؛ نگاشت مقادیر به ترتیب ۱، ۲، ... تنظیم می‌شود.
  - **کاوه‌نگار:** `verify/lookup` با `template` و پارامترهای `token`, `token2`, `token3`.
  - **SMS.ir:** `send/verify` با شناسهٔ عددی `templateId` و `parameters` نام‌دار.
- کدهای HTTP/پاسخ provider در خطاها و گزارش موجود ارسال ثبت می‌شوند. این توسعه پیام واقعی آزمایشی ارسال نمی‌کند.
- مهاجرت `0043_sms_template_parameter_maps.sql` فقط ستون JSONB جدید با مقدار پیش‌فرض خالی اضافه می‌کند و داده‌های قبلی را دست‌کاری یا حذف نمی‌کند.

## راه‌اندازی مدیر

۱. اطلاعات دسترسی سرویس فعال و شماره خط را در «مدیریت پیامک» ثبت کنید. برای IPPanel، Access Key و شمارهٔ خط بین‌المللی مانند `+983000505` لازم است. ۲. در پنل همان سرویس قالب را بسازید و منتظر تأیید آن بمانید. ۳. در «مدیریت پیامک»، قالب رویداد مربوط را ویرایش کنید؛ شناسه/نام قالب سرویس و نگاشت دقیق هر متغیر را وارد کنید. برای IPPanel مقدار نگاشت باید دقیقاً نام placeholder ثبت‌شده در Pattern باشد؛ برای کاوه‌نگار از `token`، قاصدک `param1`، ملی‌پیامک شمارهٔ ترتیب (`1`, `2`, ...) و SMS.ir/مدیانا نام placeholder استفاده کنید. ۴. مقدارهای نمایشی را با قرارداد همان قالب تطبیق دهید؛ سامانه به‌تنهایی نمی‌تواند تأیید پنل یا تطابق متن ثبت‌شده در پنل بیرونی را تشخیص دهد.

## محدودیت‌های فعلی

- وضعیت «کلید ثبت شده» وجود اعتبار، شارژ، مجوز API، تأیید پترن یا تحویل نهایی را اثبات نمی‌کند. انجام این راستی‌آزمایی نیازمند اعتبارنامهٔ واقعی و ارسال کنترل‌شده به شمارهٔ مجاز است؛ چنین پیامکی در این مرحله ارسال نشده است.
- داشبورد SMS نشانگر سلامت سرویس از endpoint اعتبارسنجی هر provider و مشاهدهٔ وضعیت تحویل با شناسهٔ برگشتی هنوز اضافه نشده است.
- نام‌گذاری پارامترها و محدودیت تعداد متغیرها متفاوت است؛ پیش از فعال‌کردن قالب باید نگاشت را طبق پنل مقصد بازبینی کرد. برای کاوه‌نگار حداکثر سه token و برای قاصدک حداکثر ده پارامتر پشتیبانی می‌شود.
- **IPPanel:** اتصال عملیاتی نیز اضافه شد. API Edge رسمی روی `POST https://edge.ippanel.com/v1/api/send` برای ارسال عادی با `sending_type: webservice` و الگو با `sending_type: pattern` استفاده می‌شود. کلید با هدر `Authorization` فرستاده می‌شود؛ فرستنده و گیرنده در قالب E.164 هستند. برای الگو، `Pattern Code` در شناسهٔ قالب و نام دقیق placeholderها در نگاشت متغیر ذخیره می‌شوند. پاسخ تنها وقتی پذیرفته می‌شود که HTTP موفق و `meta.status === true` باشد؛ پاسخ API نیز در گزارش ارسال باقی می‌ماند. شماره‌های موبایل محلی `09…` به `+989…` تبدیل می‌شوند.

## مرحلهٔ IPPanel تکمیل شد

- IPPanel به فهرست سرویس‌های پنل پیامک مدیر و پنل اختصاصی باشگاه فروشنده اضافه شد.
- ارسال عادی، ارسال الگو، نگاشت نام placeholder، تبدیل شمارهٔ گیرنده به E.164، اعتبارسنجی پاسخ API، timeout و ذخیرهٔ پاسخ برای عیب‌یابی پیاده شد.
- ارسال پیام متنی باشگاه فروشنده نیز از اتصال IPPanel استفاده می‌کند و پیش از فعال‌سازی، کلید و شمارهٔ خط را لازم دارد.
- تنظیمات جدید به schema یا دیتابیس اضافه نشد؛ از فیلدهای فعلی کلید API و شمارهٔ فرستنده استفاده می‌شود. هیچ مهاجرت دیتابیسی لازم نیست.
- پیاده‌سازی بر اساس [مستند رسمی الگوی IPPanel](https://ippanelcom.github.io/Edge-Document/docs/send/pattern/) و [مستند رسمی ارسال عادی](https://ippanelcom.github.io/Edge-Document/docs/send/webservice/) انجام شد.

## مرحلهٔ بعد

مسیر شکاف #۶ برای افزودن سرویس‌دهنده‌های پیامک تکمیل شد. قابلیت باقیماندهٔ داخل همین حوزه، صفحهٔ سلامت/اعتبارسنجی اتصال و پیگیری وضعیت تحویل با شناسه‌های برگشتی provider است؛ این کار باید جداگانه انجام شود چون API و عمر شناسه‌ها میان سرویس‌ها یکسان نیست. در نقشهٔ شکاف‌های سایت، شروع بعدی مورد **۷: نمودار تاریخچهٔ قیمت محصول** است. هیچ پیام واقعی برای آزمون این مرحله ارسال نشده است.
