# شکاف‌های مشخصات برای بازسازی و توسعهٔ دقیق

این فایل فرق میان «کد موجود»، «مستند فعلی» و «اطلاعاتی که هنوز برای بازتولید دقیق محصول لازم است» را شفاف می‌کند. پیشنهادهای سطح P0/P1 زیر کمبود مستندات‌اند و الزاماً به معنی نبودن قابلیت در کد نیستند.

## وضعیت شواهد فعلی

- routeهای App Router، خانواده‌های API، مدل‌های مهم، سرویس‌های دامنه و ریسک‌های شناخته‌شده مستند شده‌اند.
- برای هر ماژول معیارهای پذیرش اضافه شده‌اند؛ این معیارها specification پیشنهادی‌اند و خودبه‌خود نشان نمی‌دهند implementation فعلی آن‌ها را پاس کرده است.
- schema و API به‌طور کامل به جدول فیلدبه‌فیلد و endpointبهendpoint تبدیل نشده‌اند. مستندات جای خواندن فایل/کد جاری را نمی‌گیرند.
- مستندات تصویری صفحه‌ها، interactionهای دقیق، نمونهٔ دادهٔ مجاز، و خروجی‌های مرجع (فاکتور/لیبل/گزارش) ندارند؛ بنابراین pixel-perfect reproduction از Markdown ممکن نیست.
- فرم محصول، گردش سبد/checkout، صفحهٔ POS، انواع سند انبار و بخش‌های گزارش حسابداری اکنون بر اساس صفحه/سرویس‌های اصلی با جزئیات بیشتر توصیف شده‌اند؛ با این حال همهٔ input/outputهای API و همهٔ postingهای مالی هنوز به ماتریس ردیف‌به‌ردیف تبدیل نشده‌اند.
- برای کمپین‌ها call-site داخلی موجود است: `src/instrumentation.ts` تابع `processCampaigns()` را هر ۶۰ ثانیه صدا می‌زند. بااین‌حال تضمین اجرا در چند process/replica، lifecycle سرور، idempotency بین replicaها و log/monitoring production باید جدا بررسی شود.
- ledger انبار هنوز چندمنبعی است: انبار default از `products`/`product_variants`، انبار دیگر از `inventory_warehouse_stock` و انبار seller در برخی عملیات از `seller_offers` خوانده می‌شود. queryهای تجمیعی/صادرات و reconciliation باید هر دامنه را بدون دوباره‌شماری تفکیک کنند.
- بعضی گزارش حسابداری UI از جمع journal می‌آیند، ولی گزارش حسابداری صنعتی فعلی از query سفارش‌های ارسال/تحویل استفاده می‌کند؛ دامنهٔ شمول آن با POS، تعدیل و مرجوعی باید با صاحب محصول تأیید و کد تطبیق داده شود.
- سند چندقلمی انبار اقلام را JSONB نگه می‌دارد. پذیرش حواله مقدار بیشتر از مقدار صادرشده را به موجودی اضافه نمی‌کند و اختلاف را ثبت می‌کند؛ سیاست کسب‌وکار برای موجودی اضافه و مسیر اصلاح سند نیازمند تصمیم روشن است.
- فرم محصول دارای یک ناسازگاری مشاهده‌شده بین عنوان ورودی شناسه (شمارهٔ گواهی ارگانیک) و دادهٔ OEM/شماره قطعه است. پیش از واردکردن اطلاعات گسترده، این mapping باید با مالک داده تعیین تکلیف شود.
- جست‌وجوی فایل/پوشه، متن مخزن، `package.json`، تاریخچهٔ commit و مستندات فعلی، نام/پوشه‌ای با `rozetti_shop` پیدا نکرد؛ مخزن نیز package یا Git repository تو‌در‌تو ندارد. بنابراین در وضعیت فعلی مدرکی برای حضور مستقیم پروژهٔ Rozetti نداریم.
- بااین‌حال بقایای اصطلاحات خودرو قطعی‌اند: component و helper به نام `VehicleFinder`/`vehicleMakes`, پارامتر query به نام `make`, ستون‌های `carMake/carModel/carYear/vin` و method مقدار `vehicle`. UI و seed فعلی آن‌ها را برای suitability ارگانیک، برند/نوع/وزن و بارکد بازاستفاده می‌کنند. مستندات باید این را به‌عنوان نام‌گذاری legacy بیان کنند؛ منشأ آن را بدون مقایسه با نسخهٔ Rozetti نسبت ندهند.

## P0 — لازم برای پیاده‌سازی امن

### ۱. فرهنگ داده و API

برای هر API یک ردیف استاندارد ثبت شود: method، pattern، احراز هویت، permission، ورودی، پاسخ، خطاها، transaction، side effects و فایل handler. برای هر جدول حیاتی، ستون، nullability، unique/FK/index، lifecycle، منبع داده و migration معرفی شود. نقطهٔ شروع: `src/lib/api/*.ts`, route aggregator و `src/db/schema.ts`.

### ۲. ماشین حالت‌های مالی و سفارش

جدول انتقال‌های مجاز برای order، shipment، payment، return، supply quote، inventory document، seller KYC و withdrawal تکمیل شود. برای هر transition: actor مجاز، precondition، side effect مالی/موجودی، notification، reversal و event audit ثبت شود.

### ۳. سیاست‌های اعداد و قیمت

واحد داخلی پول، واحد نمایش، rounding، VAT/tax، روش ترکیب تخفیف‌ها، سقف تخفیف، منبع بهای خرید، قواعد قیمت پلکانی، نرخ ارز، کارمزد seller، shipping و تبدیل امتیاز با نمونهٔ عددی رسمی ثبت شوند.

### ۴. عملیات production و بازیابی

فهرست نام متغیرهای محیطی (بدون مقدار secret)، نیازمندی Node/Postgres/PM2، migration قبل/بعد deploy، storage mount/backup، کلید امضای update، pg_dump/restore drill، health check، log rotation و راه rollback ثبت شود. secret واقعی وارد سند نشود.

### ۵. قرارداد مالی و انبار قابل reconciliation

برای هر flow واقعی، یک ماتریس «محرک → journal lines → stock movement → کیف/پرداخت → مرجع» تولید شود: خرید، دریافت امانی، فروش POS مرکزی و فروشنده، سفارش آنلاین چندفروشنده، کارمزد، هزینه حمل، refund، لغو، تعدیل مثبت/منفی، انتقال، بسته‌بندی، کارت هدیه و برداشت. نمونه باید شامل رقم‌های anonymized و جمع دوطرفه باشد. برای هر حساب، ماهیت، ارز/واحد، تفصیلی مجاز و روش بستن دوره را مدیر مالی تأیید کند.

### ۶. ماشین حالت کامل POS/حمل/انبار

برای فاکتور POS حالت‌های ثبت/چاپ/ارسال/تحویل/لغو/مرجوعی و پیوند آن به `orders`, shipment و return request مشخص شود. برای حواله، قواعد مقدار بیشتر/کمتر، گم‌شدن، اختلاف مالکیت امانی و برگشت از ارسال تعریف شود. مشخص گردد فروش حضوریِ ارسال‌دار دقیقاً از کدام منبع صف مدیریت ارسال تغذیه می‌شود و آیا `central_pos_sales` برای همهٔ گزارش‌ها order محسوب می‌شود یا رابط مشترک دیگری لازم است.

## P1 — برای رسیدن به کیفیت و رفتار مشابه

### ۵. مرجع طراحی تصویری

برای مسیرهای اصلی screenshot light/dark در desktop/mobile، مشخصات spacing/type/color، empty/loading/error states، modal behavior، hover/focus، table responsive و پیام‌های فارسی تهیه شود. منبع مرجع باید همان نسخهٔ deploy/commit را نام ببرد.

### ۶. سناریوهای کسب‌وکار و داده

Seedهای anonymized برای محصول تک‌تنوع/چندتنوع، seller offer، مهمان و مشتری ثبت‌شده، سفارش چندفروشنده، refund، حواله با اختلاف، پس‌کرایه، تخفیف، affiliate و روز تولد ایجاد شود. مقدارهای حساس/مشتری واقعی در docs یا fixture نباشد.

### ۷. قراردادهای provider بیرونی

برای هر درگاه، پیامک، carrier و سرویس نقشه: مستند رسمی/نسخه، environment sandbox، request/response نمونهٔ پاک‌سازی‌شده، timeout/retry، signature/verify، نرخ محدودیت، خطای کاربرپسند و پیکربندی لازم ثبت شود. هر اتصال provider ممکن است تغییر API داشته باشد.

### ۸. SEO و محتوای editorial

قواعد title/description/canonical/robots/OG/JSON-LD، redirect slug، pagination، schema FAQ/Product/Article و کیفیت تحریریه برای کالاهای ارگانیک تعریف شود. واژه‌های ممنوع/ادعاهای درمانی بدون منبع و tone of voice ثبت شوند.

## P2 — کیفیت و نگه‌داری

- ماتریس مرورگر/viewport و keyboard/screen reader.
- معیار performance برای LCP/CLS، تصاویر و page cache.
- retention و دسترسی IP، OTP، audit، ticket و فایل خصوصی.
- فرآیند incident: بررسی خطای PM2/DB/provider، correlation id و اقدام recovery.
- قرارداد نسخه‌گذاری blockهای page builder و migration محتوای JSON قدیمی.

## اولویت پیشنهادی برای ادامهٔ مستندسازی

1. قرارداد journal و گردش موجودی را با مدیر مالی/انبار روی چند سند واقعی anonymized reconciliation کنید؛ به‌خصوص گزارش صنعتی، برگشت POS و تعدیل موجودی.
2. timer کمپین‌ها را در production از نظر چند replica، timezone، قفل، retry، توقف graceful و dashboard خطا تأیید کنید.
3. APIهای commerce، inventory، gateway و POS را به قرارداد endpoint شامل input/output و permission تبدیل کنید؛ این‌ها بیشترین ریسک مالی و موجودی دارند.
4. سیاست اختلاف پذیرش حواله، فروش POS ارسال‌دار در shipmentها و سطح تنوع انبار seller را با مالک محصول قطعی کنید.
5. مستندات تصویری light/dark و responsive از Checkout، جزئیات محصول، POS، اسناد انبار، سفارش و صفحه‌ساز تهیه کنید.
6. در پایان APIهای باقی‌مانده، گزارش‌ها، تنظیمات و runbook عملیات production تکمیل شوند.

## تکمیل این دور بررسی کد

در این دور، اسناد ماژول‌ها از فهرست قابلیت به شرح flow اجرایی ارتقا یافتند:

- [حسابداری](05-finance.md) تفاوت برگشت دستی سند با مرجوعی فیزیکی کالا، قالب روکش A4، مراحل تأیید مرجوعی سه نوع فاکتور، restore موجودی و lot امانی، کیف پول/اعتبار و مرجع‌های journal را ثبت می‌کند.
- [انبار](02-inventory.md) فرم ثبت سریع تک‌قلمی را کنار صورتحساب خرید چندقلمی نگه می‌دارد؛ فیلدهای شماره فاکتور و رسید، پرداخت، خرید/امانی، تعدیل و صدور/پذیرش حواله WT را با مقدار اختلاف و مالکیت توضیح می‌دهد.
- [بازاریابی](07-marketing-crm.md) انواع کمپین و رویداد واجد شرایط، مخاطب مرکزی و seller، گروه‌ها، رضایت، زمان‌بند ۶۰ ثانیه‌ای، batch/dedupe/retry/unknown و تمایز campaign از تخفیف و یادآوری سبد را توضیح می‌دهد.
- [وبلاگ](08-content.md) نقش نویسنده/بازبین/ناشر، وضعیت draft/review/published، اعتبارسنجی فیلدها، نیاز media، دسته/برچسب، SEO مقاله و robots، انتخاب رسانه و تأثیر انتشار روی فرانت/cache/sitemap را شرح می‌دهد.

این توصیف‌ها «رفتار کد» را از «صحت سیاست کسب‌وکار» جدا می‌کنند. دو مورد مالی نیازمند تأیید حسابدار باقی است: `addCredit` هنگام refund سند debit `1101` / credit `2103` می‌سازد، و در مسیر cash برگشت POS مرکزی ثبت مستقلی برای خروج وجه/رسید پرداخت دیده نشد. برای هر سه نوع مرجوعی باید سندهای anonymized از محیط واقعی با دفتر مالی تطبیق داده شوند. همچنین trigger زمان‌بند campaign در repository وجود دارد، اما پایداری timer و بازیابی job در topology واقعی production با مستندات و logهای deployment تأیید نشده است.

### تطبیق پنل کاربر

مسیرهای منوی `CUSTOMER_NAV` و لینک‌های داشبورد با routeهای واقعی بررسی و در [سند مشتری](06-customer.md) ثبت شدند. مواردی که در شرح قبلی کم‌رنگ/جاافتاده بودند: محتوای داشبورد و کدهای تخفیف فعال، اعلان محصول خارج از منوی اصلی، نشست‌های فعال و لغو دستگاه، پروفایل شامل تصویر/تولد/اطلاعات رسمی/رضایت پیامک، برداشت قابل پرداخت از کیف پول مشتری و بازگشت وجه هنگام رد آن، درخواست همکاری affiliate به‌عنوان ماژولی غیر از دعوت، جزئیات لغو/تأیید دریافت/مرجوعی سفارش، و quote/expiry/لغو در صفحهٔ استعلام.

در کد فعلی، withdrawal کیف پول مشتری از balance کسر می‌شود و مدیر می‌تواند `paid` یا `reject` کند؛ اما سند حسابداری/رسید بانکیِ پرداخت نهایی در همین handler مشاهده نشد. همچنین تغییر شماره تلفن از فرم پروفایل در دسترس نیست و به پشتیبانی ارجاع داده می‌شود. این دو نکته به‌عنوان رفتار/محدودیت جاری ثبت شده‌اند و تصمیم محصول یا تطبیق مالی جدا می‌خواهند.

## شکاف‌های جدید و تصمیم‌های لازم

### مالی و برگشت

برای هرکدام از سفارش آنلاین، POS مرکزی و POS فروشنده یک نمونهٔ anonymized تهیه شود که journal قبل و بعد، wallet، payment، stock movement و lot usage را کنار هم نشان دهد. حسابدار باید تأیید کند آیا برگشت نقدی POS باید journal مستقل صندوق/بانک داشته باشد، آیا refund آنلاین باید debit واقعی بانک را بزند یا بدهی کیف مشتری را بازگرداند، و درآمد/مالیات/هزینه ارسال/کارمزد در برگشت کامل و جزئی چگونه اصلاح شوند. مستند فنی فعلی اثر کد را گزارش می‌کند، نه سیاست نهایی دفتر.

### انبار و صورتحساب

مالک محصول باید مشخص کند شمارهٔ فاکتور بیرونی و شماره سند داخلی در UI/اکسل/پرینت کدام است؛ اختلاف رسید حواله چه نوع سند اصلاحی می‌خواهد؛ کالای اضافه‌ای که مقصد گزارش می‌کند چطور پذیرش جدا بگیرد؛ و انتقال موجودی بین انبار seller و central در سطح محصول یا SKU/تنوع نهایی شود. برای lotهای مخلوط owned/consigned در یک ردیف انتقال، fixture anonymized و reconciliation مقدار/ارزش لازم است.

### بازاریابی و وبلاگ

برای CRM ماتریس رسمی consent به تفکیک پیام تبلیغاتی عمومی، تولد، خوش‌آمد، پس از خرید و abandoned cart و سیاست retry وضعیت `unknown` لازم است. Segmentهای پویا را فقط وقتی مستند کنید که در query واقعی پشتیبانی شوند؛ گروه دستی فعلی معادل segmentهای «خریدار ۹۰ روز اخیر» نیست. برای blog، SLA بازبینی، rubric ادعاهای سلامت، taxonomy رسمی، اولویت metadata مقاله در برابر تنظیم عمومی و redirect هنگام تغییر slug باید با مسئول محتوا تعیین شود. سقف‌های validation در سند وبلاگ مستند شده‌اند و جایگزین policy تحریریه نیستند.
