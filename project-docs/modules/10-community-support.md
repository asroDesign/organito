# دیدگاه، پرسش‌وپاسخ و پشتیبانی

## دیدگاه و سؤال محصول

جدول‌های `reviews`, `review_votes`, `product_questions`, `product_answers`; endpointهای `src/lib/api/community.ts`. کاربر review/سؤال می‌فرستد، رأی مفیدبودن می‌دهد؛ admin می‌تواند review/question/answer را مدیریت کند. پاسخ‌ها باید به سؤال اصلی متصل باشند و فرانت همهٔ پاسخ‌های همان سؤال را نشان دهد.

## تیکت

`tickets`, `ticket_messages`, `ticket_departments`; مشتری `/customer/tickets`, فروشنده و admin `/admin/tickets`, departments، جزئیات. API در `src/lib/api/staff.ts`, `public.ts`, `extra.ts`. تیکت status/department/assignee/customer؛ پیام خصوصی/داخلی باید کنترل access داشته باشد. پنل مدیر می‌تواند تیکت جدید ایجاد کند.

## اعلان

`notifications`، API عمومی خواندن/mark read و UI در shell/صفحات مشتری. KYC، سفارش، پاسخ تیکت، پرداخت و پیام‌ها به اعلان متصل‌اند.

## قواعد دسترسی

- مالکیت مشتری براساس user یا تلفن snapshot؛ فروشنده فقط موضوعات متعلق به خودش.
- admin replies و پاسخ به دیدگاه در modal UI است؛ endpoint mutation باید permission را کنترل کند.
- حذف/رد پاسخ و حذف نرم باید با رویداد و نویسنده حفظ شوند، خصوصاً برای moderation.

## ریسک‌ها

- distinction میان پاسخ عمومی review و مکاتبهٔ خصوصی ticket باید در مدل و UI واضح بماند.
- نمایش تعداد پاسخ بدون fetch پاسخ‌ها مشکل تجربهٔ کاربری ایجاد می‌کند؛ query پاسخ‌های فرزند را با pagination/limit مناسب و ترتیب ثابت بگیرد.
- عدم moderation statusهای واضح می‌تواند پاسخ pending را عمومی کند؛ status default و query فرانت را قبل از توسعه مرور کنید.

## جریان moderation و تیکت

پرسش، پاسخ و review با شناسهٔ محصول و نویسنده ذخیره می‌شوند. صفحهٔ مدیریت باید فهرست را فیلتر کند، جزئیات پرسش را در modal یا پنل نشان دهد، تمام پاسخ‌های child را زیر پرسش قابل مشاهده کند و برای هر پاسخ عملیات تأیید/رد/حذف مجاز داشته باشد. پاسخ عمومی فقط وقتی در صفحهٔ محصول رندر شود که status آن مجاز به انتشار باشد.

تیکت از مشتری، فروشنده یا مدیر ایجاد می‌شود؛ هر پیام به تیکت و فرستنده وصل است. پیام داخلی staff نباید در customer/seller API برگردد. تغییر assignee/department/status باید actor و زمان داشته باشد؛ اعلان پاسخ باید بعد از commit ایجاد شود تا اعلان برای پیام ذخیره‌نشده ارسال نشود.

## معیارهای پذیرش

- همهٔ پاسخ‌های تأییدشدهٔ یک سؤال، به ترتیب پایدار زیر همان سؤال دیده شوند؛ پاسخ pending یا ردشده public نشود.
- پاسخ مدیر از modal قابل ارسال باشد؛ خطای validation محتوای فرم را پاک نکند.
- کاربر فقط ticket خودش را بخواند؛ seller فقط ticket مجاز/مرتبط با خود را ببیند؛ پیام داخلی برای مشتری قابل query نباشد.
- حذف پاسخ یا ticket با مجوز مناسب انجام شود و audit/history موردنیاز باقی بماند.
- ارسال اعلان پس از ثبت موفق پیام انجام شود و retry موجب duplicate notification نشود.

## تجربهٔ مشتری در پشتیبانی و اعلان‌ها

در `/customer/tickets` فرم تیکت جدید دپارتمان‌های فعال را از DB می‌گیرد و موضوع، اولویت `low/normal/high/urgent`، سفارش مرتبط اختیاری و متن پیام می‌پذیرد. پس از ثبت به `/customer/tickets/[id]` می‌رود؛ فهرست شماره، موضوع، دپارتمان، status و زمان آخرین تغییر را نشان می‌دهد. صفحهٔ جزئیات ticket را هم با `customerId` محدود می‌کند. پیام داخلی کارکنان نباید در endpoint/thread مشتری ظاهر شود؛ مشتری تیکت بسته را نمی‌تواند ادامه دهد. صفحهٔ خانه نیز چهار ticket آخر را با پیوند مستقیم نشان می‌دهد.

`NotificationBell` در header همهٔ ناحیه‌های احراز‌شده شمارش unread می‌گیرد، فهرست را از `/api/notifications` می‌خواند و امکان mark-read برای یک مورد یا همه دارد. نوتیفیکیشن یک inbox درون‌سایت است و با SMS log، campaign delivery یا ایمیل یکی نیست. برای هر notification، لینک باید به route‌ای برسد که مالکیت/نقش را مجدداً کنترل کند؛ unread count می‌تواند از این مسیرها تغذیه شود: سفارش، پاسخ تیکت، پرداخت و وضعیت KYC.
